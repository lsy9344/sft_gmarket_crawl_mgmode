>   불가" 판단은 폐기.
> - 실측 전체는 **`CRAWL_RESULTS.md`** 참조. 본 문서와 다르면 그것이 우선.

> 최종 개정: 2026-07-25 (rev.4)
> **rev.4 — 공정위(FTC) 연동 전면 제거.** 필수 수집 항목은 Coupang 자체

## Overview

Gmarket의 `mg.gmarket.co.kr` 무보호 엔드포인트 방식은 Coupang에 **그대로**
적용 불가하다(Akamai 보호 + 동적 렌더링) — 하지만 **원리는 동일하게
적용한다**: 대상 사이트 자신의 상품 상세페이지에서 판매자 사업자정보를
직접 읽는다.

**rev.4 핵심 원칙**

1. **사업자정보는 Coupang 상세페이지에서만 얻는다.** 외부 DB 연동 없음.
2. **판매자 단위로 축약한 뒤 고비용 구간에 진입한다** (D2). 상품마다
   상세를 열면 같은 사업자정보를 수십 번 재수집하게 된다.
3. **최종 산출물은 사업자번호 기준 유일하다** (D3).
4. **Stage는 독립 실행한다.** Stage C(상세 스크래핑)는 전 판매자를
   대상으로 하므로 장시간 실행이다 — Stage 경계가 체크포인트다.
5. **프록시는 선택이 아니다.** 4단계 중 2단계(A, C)가 프록시 필수이고,
   나머지 2단계(B, D)는 그 산출물 없이는 무의미하므로 사실상 전체
   파이프라인이 프록시에 의존한다.

## Collection Pipeline (rev.4 — 4 Stages)

```
┌──────────────────────────────────────────────────────────────────────┐
│                Coupang OMP 수집 파이프라인 (rev.4)                     │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  [Stage A] OMP 리스팅 스캔           [StealthySession + KR 프록시]    │
│  ├── URL: /np/omp?listSize=120&page={N}&sorter=bestAsc               │
│  │        (robots 허용 경로 우선: /np/categories/, /np/search)        │
│  ├── 추출: product_id, itemId, vendorItemId, store_name,             │
│  │        price, rating, review_count, power_seller(배지)            │
│  ├── 제어: 페이지 간 8~15초, 세션당 ≤5페이지, 일일 예산 차감         │
│  └── 산출: coupang_listing_{ts}.json  (상품 원본)                    │
│                                                                      │
│  [Stage B] 판매자 축약 (D2)          ※ 네트워크 요청 0 · 무료         │
│  ├── product_id → store_name → seller_key 정규화 축약                │
│  │       수천 상품 → 수백 판매자  ★ 고비용 진입 전                    │
│  ├── 기확보 사업자 스킵 (business_index 역인덱스 조회)                │
│  └── 산출: 방문 대상 판매자 목록 (판매자당 대표 상품 1건)             │
│                                                                      │
│  [Stage C] 판매자 상세 직접 스크래핑  [StealthySession + KR 프록시]   │  ★ 사업자정보 유일 경로
│  ├── 대상: Stage B 로 축약된 **모든** 판매자                         │
│  ├── 방법: 대표 상품 1건 → 상세페이지 최하단 사업자정보 란 파싱       │
│  │         (최하단 DOM 파싱 1순위, XHR 캡처는 폴백)                  │
│  ├── 획득: company_name, ceo_name, business_number, address, phone,  │
│  │        (파워셀러 배지)                                            │
│  │        — Gmarket mg.* 와 동일한 원리, 외부 DB 없음                │
│  ├── 실패 시: 재시도 → 그래도 실패면 미확정으로 분리 (대체 경로 없음) │
│  ├── 제어: 배치 5건/세션, 쿨다운 600~900초, 차단 2회 시 중단          │
│  └── 산출: 판매자 프로필 캐시 갱신 (건 단위 durable 저장)            │
│                                                                      │
│  [Stage D] 사업자 단위 집계 + 출력   ※ 로컬                          │
│  ├── D3: 동일 사업자번호 중복 제거                                    │
│  │       - 숫자 10자리 정규화 + 국세청 체크섬 검증                    │
│  │       - 대표 레코드 선택 (필드 충족도 → 수집순)                   │
│  │       - 병합: store_names/store_count/product_count               │
│  │               power_seller = OR                                   │
│  ├── business_index 갱신 (다음 실행에서 즉시 스킵)                    │
│  └── 산출: coupang_business_{ts}.json/.csv   ← 사업자번호 유일        │
│           coupang_unresolved_{ts}.json/.csv ← 상세 실패 판매자 분리   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 이전 판 대비 변경점

| 항목 | rev.1~3 | **rev.4 (최종)** |
|------|---------|-------------------|
| 단계 수 | 5~6단계 (공정위 적재/매칭/보강 포함) | **4단계** |
| 사업자정보 확보처 | 공정위 DB (전부 또는 일부) | **Coupang 상세페이지, 유일한 경로** |
| Stage C 방문 대상 | 공정위 미매칭 판매자만 (rev.2) | **Stage B 로 축약된 전체 판매자** |
| 외부 의존성 | SQLite+FTS5, thefuzz, python-Levenshtein | **없음** |
| 오매칭 리스크 | 퍼지 매칭 모호성이 주 리스크 | **없음** (파싱 실패/차단만 리스크) |
| 실패 시 대체 경로 | 공정위 폴백 | **없음** — 재시도 후 미확정 분리 |

### 처리량 산정

OMP 5페이지 = 600상품, 판매자 중복도 2.5 → 고유 판매자 240명.

| 방식 | 상세 fetch 수 | 소요 (상각 165초/건) |
|------|-------------|--------------------|
| 상품 단위 (D2 없음) | 600 | 약 27시간 |
| **rev.4/5 (판매자 단위, 전원 방문)** | **240** | **약 11시간** |

*상각 165초/건 = 세션 내 지연 12초 + 웜업 상호작용 3초(rev.5) + 쿨다운
750초 ÷ 배치 5건.* rev.4의 150초 추정에 웜업 상호작용 시간이 추가됐다.
**D2(판매자 단위 축약)가 유일한 비용 절감 수단이다** — 외부 DB로 방문
자체를 건너뛸 방법은 없다.

> **rev.5 참고.** 적응적 백오프(`AdaptiveBackoff`)가 발동하면 배치 크기가
> 3~4건으로 줄고 쿨다운이 ×2~×4 배가 되어 실제 소요는 더 늘어난다.
> 위 수치는 차단 0회 이상 조건이다.

### 세션 레벨 안티탐지 전략 (rev.5 신규)

처리량보다 **차단율 0% 유지**가 우선이다. 아래 전략이 처리량을 약 10~15%
감소시키지만, 차단으로 인한 IP 평판 손실과 복구 대기(15~30분/회)가 훨씬
큰 비용이다.

| 전략 | 모듈 | 효과 |
|------|------|------|
| 웜업 상호작용 주입 | `behavior.py` `warmup_interact()` | 센서 텔레메트리 생성 — "대기만" 시그니처 제거 |
| 세션 간 랜덤화 | `randomizer.py` `SessionRandomizer` | 배치·정렬·타이밍·decoy 방문 랜덤화 |
| 프록시 canary | `proxy.py` `_canary()` | flagged IP 사전 차단 |
| 적응적 백오프 | `backoff.py` `AdaptiveBackoff` | 차단 누적 시 점진적 완화 (쿨다운×N, 배치-N) |
| 파서 건강 모니터링 | `health.py` `ParserHealthMonitor` | XHR/DOM 성공률 추적 → 변경 조기 감지 |

전체 구현: `BYPASS_TECHNICAL_GUIDE.md` §11~§15, `IMPLEMENTATION_PLAN.md` §9.3~§9.7.

## Collection Routes (재평가)

5가지 경로 중 채택 경로는 하나뿐이다.

### 채택: StealthySession 직접 스크래핑 (Gmarket `mg.*` 방식의 Coupang 대응)

Verified tech stack: Scrapling `StealthySession`(Camoufox 엔진) + 한국
주거용 프록시. 기존 프로젝트가 이미 `scrapling[fetchers]>=0.4.11` 을
사용하므로 신규 핵심 의존성 없이 확장 가능하다.

| 항목 | Gmarket | Coupang (rev.4) |
|------|---------|------------------|
| 웜업 | 3~5초 | 8~15초 (70KB `_abck` 센서) |
| 배치 | 제한 없음(HTTP) | 3~5건/세션 |
| 쿨다운 | 없음 | 600~900초 |
| 요청 간격 | 0.5초 + jitter | 5~15초 |
| 차단 허용 | 3회 | 2회 |
| 프록시 | 불필요 | **필수** |
| **사업자정보 획득 방식** | `mg.*` GET → BS4 파싱 | **StealthySession fetch → XHR/DOM 파싱** (원리 동일) |
| **판매자정보 확보 경로** | 단일 (mg.* 엔드포인트) | **단일 (상세페이지) — 대체 경로 없음** |

**Akamai 5계층 대비 커버리지** (`SCRAPLING_TECH_ANALYSIS.md` §4.1)

| 계층 | 대응 | 우리 코드 필요? |
|------|------|----------------|
| L1 TLS/HTTP 핑거프린트 | Camoufox 실제 Firefox 스택 | 불필요 |
| L2 JS 챌린지(`_abck`) | 실브라우저 센서 실행 | 웜업 대기만 |
| L3 브라우저 핑거프린트 | C++ 레벨 스푸핑 + BrowserForge | 불필요 |
| **L4 행동 분석** | C++ 마우스 궤적 | **필요** — 지연/스크롤/유입체인 |
| **L5 IP 평판** | 없음 | **필요** — 한국 주거용 프록시 |

### 기각/보류된 경로

| 경로 | 상태 | 사유 |
|------|------|------|
| 공정위 DB 매칭/보강 | **제거 (rev.4)** | 필수 항목이 이미 대상 사이트 자체에 존재 — 외부 DB 불필요 |
| Selenium + Chromium 108 | 채택 안 함 | Camoufox의 C++ 레벨 스푸핑이 JS 삽입보다 탐지 위험 낮음 |

| 모바일 앱 API 인터셉트 | 채택하지 않음 | SSL Pinning 우회는 법적 리스크 큼 |

## Recommended Execution Order (rev.4)

| 순서 | Stage | 프록시 필요 | 소요 | 비고 |
|------|-------|-----------|------|------|
| 1 | A. OMP 리스팅 스캔 | ✅ | 페이지당 10~20초 | 일일 예산 차감 |
| 2 | B. 판매자 축약(D2) | ❌ | 수 초 | 네트워크 요청 0 |
| 3 | **C. 판매자 상세 직접 스크래핑** | **✅** | **판매자당 상각 150초** | **★ 사업자정보의 유일한 경로** |
| 4 | D. 사업자 집계 + 출력 | ❌ | 수 초 | D3 중복 제거 |

**프록시 미확보 시**: **파이프라인 전체가 동작하지 않는다.** Stage A
없이는 판매자 목록을 얻을 수 없고, Stage C 없이는 사업자정보를 얻을 수
없다. 프록시 예산 집행은 이 프로젝트의 실행 전제조건이다
(`IMPLEMENTATION_PLAN.md` §17-Q2).

**Stage 재실행 규칙**
- Stage A: 신규 상품 발굴 시 (예산 범위 내)
- Stage B: Stage A 이후 항상 (무료)
- Stage C: Stage B 결과 중 미방문 판매자가 남아 있고 예산이 있을 때
- Stage D: 언제든 (누적 데이터로 재집계)

## 수집 항목 특이사항 반영

### 1. 동일 사업자번호 제거

변경 없음 — `DATA_FIELDS_MAPPING.md` §3, `IMPLEMENTATION_PLAN.md` AD-10.
D3 입력값은 이제 **상세페이지 직접 파싱 결과 하나뿐**이다.

### 2. 파워셀러 여부

변경 없음 — `DATA_FIELDS_MAPPING.md` §4, `IMPLEMENTATION_PLAN.md` AD-11.
Stage C가 전 판매자를 방문하므로 상세/XHR에서 확보하는 경로의 커버리지
제약이 사라졌다.
