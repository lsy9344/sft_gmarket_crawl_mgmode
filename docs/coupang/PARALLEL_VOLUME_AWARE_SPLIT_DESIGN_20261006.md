## 0. 결론 요약

1. **세션 최대 활용은 옳다** — 단, 쿠팡에 보이는 순간 요청 밀도(항상 브라우저
   1개)를 올리지 않고 **독립 안전 봉투(인스턴스) 수를 늘리는 방식으로만**.
   이 엔진의 설계 원리(스레드 병렬 대신 스케줄 interleaving)와 일치하며
   회선 수에 선형 비례한다.
2. **선형 확장의 3천장**이 있다 — §4. 실행 천장(순차 세션 실행 시간),
   분할 천장(작업 단위의 최소 입자), 비용 천장(Decodo 트래픽).
   본 설계는 세 가지를 모두 존중하면서 세션 활용률을 끌어올린다.
3. **핵심 변경 2단계(+1)** — ① 샤드 구성을 라운드로빈 → 물량 가중 bin-packing
   (작은 변경, 불균형 제거) ② 큰 카테고리를 페이지 범위/상품 조각으로
   분할해 "카테고리 수 < 인스턴스 수"일 때도 전 회선 활성(중간 변경)
   ③ 목록·판매자 조각을 **하나의 혼합 워크스틸링 큐**로 운영 — 역할 전용
   회선(목록 전담/판매자 전담)은 총 세션 수를 줄이지 못해 기각(§5.3).
4. 권장 상한: 인스턴스 20(`MAX_INSTANCES=20`). 현재 세션 소요(2.5~4분)
   기준 순차 실행 천장(~18~24세션/시간)의 75~85% 지점으로, 실측 대비
   안전 마진을 유지하는 최대치다.

## 1. 목표·비목표

### 목표
- 카테고리 수가 인스턴스 수보다 적어도 모든 회선이 유효 작업을 갖는다.
- 샤드 간 예상 물량 편차로 인한 꼬리(straggler) 완주을 제거한다.
  (실측: 같은 라운드에서 샤드1 3P 6개 vs 샤드3 377개 — 60배)
- 안전 봉투(인스턴스별 80분 간격, 한 시점 브라우저 1개, 가드 장부,
  차단 시 해당 인스턴스만 격리)를 절대 약화하지 않는다.
- 같은 출력 폴더 재시작(이어서 수집) 규약을 그대로 유지한다.

### 비목표 (명시적으로 하지 않는다)
- 스레드/브라우저 동시 병렬 — 차단 리스크·프로필 경합으로 기각(원설계 §5).
- 80분 봉투 단축 — 안전 체계의 핵심이므로 건드리지 않는다.
- 회전(무세션) 프록시 — 셸 무한으로 실증 기각(DECODO_PROXY_METHODOLOGY D5).

## 2. 현재 구조와 실측 (변경의 출발점)

### 규칙 (app/core/coupang/parallel_manager.py)
- 샤드 수 = `min(카테고리 수, 인스턴스 수 × 2)` (`SHARDS_PER_INSTANCE=2`)
- 분할 = 트리 순서 라운드로빈 `index % 샤드수` (크기를 모르므로 교차 분할)
- 카테고리 수 < 인스턴스 수 → **인스턴스 수를 카테고리 수로 축소** 안내
  (리프는 더 못 쪼갠다 — `coupang_parallel_panel.build_run_config`)
- 배정: 샤드 1..N을 인스턴스에 1:1, 잔여는 대기 큐 → 완주 시 승계(워크스틸링)
- 세션: 인스턴스당 80분 간격, 목록 8페이지/세션 또는 판매자 130상품/세션,
  **순차 실행(한 시점 브라우저 1개)**

## 3. 천장 3종 — "세션 최대 활용"이 효율이기 위해 존중해야 할 물리

### 3.1 실행 천장 (가장 중요)
세션은 순차 실행이므로 처리량 상한은 `60분 ÷ 세션 벽시간 T`이다.
- T=3분 → 최대 ~20세션/시간. 인스턴스 N개의 수요는 `0.75×N`세션/시간
  (80분당 1개)이므로 **교차점 N\* ≈ 20~32**.
- N=20: 수요 15/시간 vs 용량 ~18~20/시간 → 포화 75~85%. 마진은 얇지만
  안전(각 인스턴스의 다음 예정 = 자기 세션 종료 + 80분은 항상 보장됨).
  N을 그 이상 올리면 속도가 더 나오지 않고 큐잉만 생긴다.
- **주의 — "7이나 20이나 비슷"이 아니다.** 7회선(수요 5.3/시간, 상한의
  26%)과 20회선(15/시간, 75%) 사이는 거의 선형으로 **약 2.7~2.9배**
  차이난다. 차이가 사라지는 건 N≈27(포화) 너머다. 단, 20회선을 먹일
  작업 단위가 필요하다(§5.2 — 카테고리 수 상한 극복 전제).
- T가 나빠지면(느린 페이지) N\*는 내려간다. 스케줄러는 이미 우아하게
  대응(예정 시각이 밀려도 간격 규약은 유지)하지만, 설계 상한을
  실측 T와 함께 20으로 두고 모니터링한다.

### 3.2 분할 천장
작업 최소 입자 = 카테고리 → 카테고리 수 < N이면 회선이 놀거나 축소된다.
→ §5의 볼륨 인지 분할(본 설계의 핵심)로 제거.

### 3.3 비용·계정 천장
- 총 트래픽은 동일(시간 압축일 뿐). 과거 실측 비례 채소 전체 ≈ 0.5~1GB.
- 동시 스티키 세션 수는 Decodo 플랜 확인 필요(대시보드).
- 회선 점검(출구 IP 확인)은 쿠팡 트래픽 0, 세션당 1회 — N=20이어도 무시 가능.

**의견(결론)**: "세션 최대 활용 = 효율"은 위 3천장 안에서 참이다. 밀도를
올리는 방식(봉투 단축·동시 브라우저)은 차단 리스크로 효율이 아니라
리스크 비용이 된다. 본 설계는 봉투 수(=회선 수)를 최대한으로 올리고
봉투 하나하나가 끊김 없이 일감을 갖게 하는 방향이다.

## 4. 물량 정보 조달 — 공짜 소스가 이미 있다

### 1순위: 트리 API의 `productCount`
카테고리 새로고침이 받는 `/n-api/web-adapter/category-list` 응답에
상품 수 필드(`productCount`)가 실려 온다(2026-10-06 응답 덤프에서 gnb
레벨에서 확인). **노드별 부착 여부를 1회 검증** 후 파서가 id·이름과 함께
보존 → 추가 요청 0회로 물량 스냅숏 확보.
- 주의: 스냅숇 값. 계획 수립([수집 시작] 시점) 시점의 최신 트리 기준이며,
  stale해도 §5 알고리즘은 근사로만 사용(정확도 요구 아님).

### 2순위: 경량 계획 조사(폴백)
`productCount`가 없는 노드는 목록 1페이지 probe(카테고리당 요청 1회,
직접 회선)로 크기 추정. 쿠팡 접촉이므로 총 N회 이하로 제한하고 사용자에게
"계획 조사 중" 진행 표시.

### 3순위: 균등 분할(현행 유지)
물량을 전혀 모르면 현재의 라운드로빈으로 동작 — 열화 호환.

## 5. 계획 알고리즘 (단일 카테고리 분할 모드 확장)

### 5.1 1단계 — 가중 bin-packing (작은 변경)
```
입력: 가족 카테고리 [(id, 이름, productCount)], 인스턴스 수 N
샤드 수 S = min(카테고리 수, 2N)          # 현행 유지(스틸링 여유 2배)
목표 물량 G = 총물량 / S
카테고리를 productCount 내림차순 정렬 → 현재 물량이 가장 적은 샤드에
         배정(최장 처리 시간 우선 greedy, LPT)
```
- 효과: 샤드 완주 시간 편차 제거(60배 → 목표 ±소수 배 이내).
- 세션 1개가 8페이지/130상품으로 잘리는 현행 제약은 그대로(봉투 보존).

### 5.2 2단계 — 큰 카테고리 내부 분할 (진짜 해법)
물량이 `2G` 초과인 카테고리는 작은 조각으로 쪼갠다:
- **목록 조각**: (카테고리, 시작페이지, 종료페이지) — 예: 32페이지짜리
  카테고리를 8페이지 × 4조각. 각 조각은 자기 shard 폴더에 독립 상태로
  수집(폴더 규약은 현행 shard_NN 재사용).
- **판매자 조각**: 목록 완료 카테고리의 상품 목록(top_products.csv)을
  vendor_item_id 해시로 서로소 K조각 분할 → 각 조각이 인스턴스에 배정.
  (시간을 지배하는 단계가 판매자 매핑이므로 여기가 최고 수익 지점)
- 작업 단위 스키마 확장:
  `{"kind": "whole"|"pages"|"sellers", "category_id", "page_from", "page_to", "seller_slice"}`
- 병합: 상품은 vendor_item_id, 판매자는 vendor_id dedupe — **규약 이미
  존재**(샤드 병합 머신, 실측 중복 18.3% 정리에 사용 중). 조각 경계
  중복 스캔의 최악 결과는 재수집(트래픽 낭비)뿐, 데이터 오염 없음.

### 5.3 단계 혼합 큐 — 목록·판매자 조각이 하나의 워크스틸링 큐로

단계별 특성(§2 실측): 목록은 총 세션의 ~35~40%(카테고리당 1~2세션에
소진), 판매자 매핑이 ~60~65%로 시간을 지배한다. 판매자는 "그 카테고리의
목록이 끝난 뒤"라는 의존성만 지키면 언제든 어느 회선에서든 병행 가능하다.

- **기각안 — 역할 전용 회선**(목록 전담 / 판매자·완성 전담): 세션이 순차
  실행이라 총 완주 시간은 `총 세션 수 × 세션시간`이 결정하는데, 전담은
  총 세션 수를 줄이지 못하고 "내 단계 일감은 없는데 다른 단계 일감이
  밀려 있는" 유휴 회선만 만든다(2026-10-06 사용자 검토로 기각).
- **채택안 — 혼합 큐**: §5.2의 작업 단위(`pages`/`sellers`)를 동일한 대기
  큐에 넣는다. `sellers` 조각은 해당 카테고리의 목록 완료 순간 배출되고,
  다음 도래한 아무 인스턴스나 가져간다. 의존성은 배출 규칙(목록 완료
  카테고리에서만 판매자 조각 생성)으로 자연 보존된다.
- **효과**: 어떤 회선도 굶지 않는다 — 목록이 초반에 소진돼도 판매자
  조각이 즉시 그 회선을 채운다. 완주 시간이 "가장 무거운 경로"가 아니라
  "총 세션 수 ÷ 가동 회선 수"로 수렴한다. 채소 규모 기준 1~2라운드,
  큰 가족(식품 등)에서 그 이상 단축.
- **구현**: 매니저의 대기 큐·승계 규약은 이미 단위 종류와 무관하게
  동작하므로, `choose_action`의 단계 판단을 "샤드 소유 시점의 고정
  순서"에서 "큐 배출 규칙"으로 이관하는 것이 이 변경의 전부다.

### 5.4 배정·운영 (변경 없음)
- 작업 단위 목록을 인스턴스에 1:1, 잔여 대기 큐, 완주 시 승계(스틸링) — 단위 종류(통짜/목록조각/판매자조각)와 무관 동일 규칙.
- 인스턴스별 80분 봉투, 가드 장부, 차단 격리, sid 네임스페이스(i{N}0 십진
  10단위 — 20번 인스턴스=i200대, 2번(i20대)과 문자열 충돌 없음) 모두 유지.

### 5.5 재시작·호환
- 작업 단위 스키마가 달라지므로 매니저 상태 파일에 `plan_version` 추가.
  구버전 상태(오늘 형식)는 이전 규약(통짜 샤드)으로 그대로 재개 —
  같은 폴더 이어받기 보장. 신규 실행만 새 배분.

## 8. 테스트 계획

1. 단위: LPT packing 균등성/결정성, 조각 분할 서로소성, sid 20인스턴스 유일성,
   혼합 큐 배출 규칙(목록 완료 전 sellers 조각 미배출·완료 후 즉시 배출).
2. 통합: 가짜 브라우저 팩토리(기존 패턴)로 목록/판매자 조각 수집·병합.
3. 내구성: 기존 7인스턴트 지구력 시뮬 확장 — 20인스턴스 × 세션 사망 주입·
   중간 재시작·완주 승계.
4. 라이브 단계 검증: 8 → 14 → 20 순서, 각 단계 차단 0·활성 회선 수 기록.

## 9. 롤아웃

- Phase 1(작음): `productCount` 보존 + 가중 packing. 위험 최소, 즉시 효과.
- Phase 2(중간): 카테고리 내 조각 분할 + `MAX_INSTANCES=20`.
- 현재 진행 중인 채소 7회선 실행은 방해하지 않고 완주 후 적용.
  (완주 예상: 10-07 새벽. 병합·재개 규약 변경이 없으므로 무관.)

## 10. 미결정 사항 (사용자 결정)

- 상한 20 확정 여부(실행 천장 마진 §3.1 참고 — 16~20 모두 합리적).
- `productCount` 노드별 부착 검증 결과에 따른 폴백 우선순위.
- 판매자 조각 분할의 K 기본값(권장: 인스턴스 수와 동일하게 자동).
