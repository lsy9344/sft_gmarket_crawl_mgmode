# 쿠팡 수집 병렬 확장 설계 — 한 호스트에서 인스턴스 N개 × 회선 분리

- 작성: 2026-10-01 (핸드오프 [HANDOFF_PARALLEL_SCALE_OUT_20261001.md](HANDOFF_PARALLEL_SCALE_OUT_20261001.md)의 §6 제안을 검토·확정한 설계문서)
- 상태: **설계 완료 — 구현 착수 전.** 착수 조건은 §11.
- 검토 대상: 이 워크트리(`experiment/coupang-patchright-canary`)의 쿠팡 파이프라인
  (느리지만 현재까지 무차단으로 운영 중인 80분 예약 봉투)을 같은 Windows
  호스트에서 2~3개로 병렬화해 총 수집량을 늘리는 방안.

## 0. 검토 결론 (요약)

**병렬 확장은 가능하다. 단, "띄운 수만큼 정확히 N배"는 보장되지 않는다.**

| 항목 | 판정 | 근거 |
|---|---|---|
| 한 호스트에서 인스턴스 2~3개 동시 실행 | ✅ 가능 | 실행 CLI가 이미 `--output-dir`/`--state-root`/`--profile-root`를 받음. `user_data_dir`가 다르면 Chrome 동시 실행됨. 예약 작업도 이름별 분리 가능 |
| 회선(출구 IP) 분리 | ✅ 가능, **코드 1곳 추가 필요** | `patchright_browser()`에 프록시 인자가 없는 것이 유일한 코어 결함. 메인 워크트리 `app/core/decodo.py`의 `sticky_proxy_dict()` 반환값을 그대로 넘기면 됨 |
| 회선이 다르면 독립 평판 → 수집량 선형 증가 | ⚠️ 근거는 있음, 예외 있음 | 회선 단위 독립성 실측 4건(§2.1). 단 **Decodo 풀 단위 차단 에피소드 3회**는 세션·IP가 달라도 B/C가 동시에 다운되는 상관 실패 모드(§2.2) |
| 같은 지문(Chrome) + 상이 IP의 상관 감지 | ❓ 미지 | 유해하다는 직접 증거도 무해하다는 증거도 없음. 완화책(오프셋·프로필 독립) + 감지 규칙(§7.2)으로 대응 |
| Windows Sandbox 병용 | ❌ 불필요 | 호스트당 1 인스턴스 한계 + 휘발성. 병렬 장치가 아니므로 제외 |

현실적 기대치:

- **A(집 회선 직접)는 Decodo 풀 차단과 무관하게 계속 돈다** — 9/29 08:25~08:31
  실측에서 "집 직접 32건 통과 + 새 Decodo 3회선 전원 403"이 공존(§2.1).
- B, C는 둘 다 Decodo KR 풀을 쓰므로 **풀 차단 시 함께 다운**된다. 풀 차단은
  지금까지 고부하 진단 기간(9/27~29)에만 관측됐고 완만한 단독 운용 중
  (9/30~10/01 patchright 캠페인, 무차단)에는 관측되지 않았다. 재발 빈도는
  B 카나리 실측으로만 알 수 있다.
- 따라서 2구성(A+B)의 기대 가용 수집량은 **약 1.5~2.0배**, 3구성(A+B+C)은
  **약 2.0~3.0배** (B/C 동시 다운 확률에 따라)로 보는 것이 정직한 추정이다.

## 1. 설계 원칙

1. **인스턴스 = 5개 축의 묶음.** 회선(출구 IP) · Chrome 프로필(쿠키/이력) ·
   안전 장부(guard) · 출력 폴더 · 예약 작업. 하나라도 공유하면 독립 회선으로
   취급되지 않는다(§2.1 근거).
2. **집 회선(직접)에는 인스턴스 1개만.** 실측: "서로 다른 브라우저 프로필이나
   샌드박스를 써도 직접 공인 IP는 분리되지 않았다"
   ([SANDBOX_DIRECT_BLOCK_20260928.md](../../sft_gmarket_crawl_mgmode/docs/coupang/research/SANDBOX_DIRECT_BLOCK_20260928.md)).
   집 회선의 추가 인스턴스는 A의 평판을 가열할 뿐이다.
3. **작업 분할은 카테고리 가족 단위.** 인스턴스 간 큐/파일 공유 금지.
   한 가족(상위 카테고리 + 하위 전부)을 한 인스턴스가 목록→판매자까지
   끝낸다. 출력 파일이 인스턴스별로 갈라지므로 쓰기 충돌·이중 요청이
   원천적으로 없다.
4. **한 인스턴스 내부는 현행 순차 구조를 그대로 둔다.** 목록+판매자 병렬,
   간격 단축, 세션당 페이지 증가는 하지 않는다. 병렬화로 얻는 이득만 취하고
   검증된 봉투(세션 최대 600개·10페이지, 최소 60분 간격, 80분 예약,
   요청 사이 3초)는 인스턴스별로 동일하게 유지한다.
5. **차단 전파는 인스턴스 단위.** 한 인스턴스의 차단/503/오류는 그 인스턴스의
   예약만 끈다(현행 `run_patchright_top1000.ps1` 동작). 단 §7.2의 전역
   정지 조건은 예외.

### 2.3 운용 규율 (느린 실행 검토에서 확정된 것)

- 느린 실행의 성공 요인은 "한 번에 처리하는 양 제한 + 실행 간 간격"이지
  대기 초 단위 조정이 아니다 ([PATCHRIGHT_SLOW_RUN_REVIEW_20260928.md](../../sft_gmarket_crawl_mgmode/docs/coupang/research/PATCHRIGHT_SLOW_RUN_REVIEW_20260928.md)).
  병렬화는 이 봉투를 그대로 인스턴스 수만큼 복제하는 것이므로 원칙에 부합.
- 스티키 세션: `sessionduration-1440`(24시간 상한), **회전(무세션) 절대 금지**,
  세션 교체 = 새 IP, 쿠키-불일치 회선 금지 ([DECODO_PROXY_METHODOLOGY_20260910.md](../../sft_gmarket_crawl_mgmode/docs/coupang/DECODO_PROXY_METHODOLOGY_20260910.md)).
- 실수집 중 같은 회선의 다른 쿠팡 트래픽(진단 포함) 금지 — 폰 포함.

## 3. 인스턴스 아키텍처

### 3.1 인스턴스 정의 (3개 기준 최종형)

| 축 | A (현재) | B (1차 추가) | C (2차 추가) |
|---|---|---|---|
| 회선 | 집 회선 직접 (프록시 없음) | Decodo 스티키 세션 `sid=b01` | Decodo 스티키 세션 `sid=c01` |
| Chrome 프로필 | `%LOCALAPPDATA%\SellerCollectorPatchrightCanary\chrome_profile` | `...\Canary_B\chrome_profile` | `...\Canary_C\chrome_profile` |
| 안전 장부 | `%LOCALAPPDATA%\SellerCollectorPatchrightCanary\canary_guard.json` | `...\Canary_B\canary_guard.json` | `...\Canary_C\canary_guard.json` |
| 출력 폴더 | `Desktop\PatchrightTop1000` | `Desktop\PatchrightTop1000_B` | `Desktop\PatchrightTop1000_C` |
| 예약 작업명 | `PatchrightTop1000-80Min` (현행 유지) | `PatchrightTop1000B-80Min` | `PatchrightTop1000C-80Min` |
| 시작 오프셋 | 기준 (예: 매 시 :05) | +27분 | +53분 |
| 담당 가족 | 현재 캠페인(견과/건과+축산) → 이후 신규 가족 | 신규 가족 1 (§10.2 결정) | 신규 가족 2 (§10.2 결정) |
| 세션 봉투 | 현행과 동일: 세션 최대 8페이지·480 위치(목록) 또는 상품 130개(판매자), 요청 사이 3초, 최소 60분 간격, 80분 예약 | 동일 | 동일 |

- 프로필은 장부(`--state-root`)에서 파생하므로 **장부 폴더만 나누면 프로필은
  자동 분리**된다(현행 `profile_dir(state_root)` 구조).
- 오프셋 27분/53분: 80분 주기 3인스턴스의 시작 시각 간격을 27/26/27분으로
  벌려 같은 시각 집중을 없앤다. 2구성(A+B)에서는 B를 +40분에 둔다.
- 집 회선 NAT 뒤로 A·B·C의 물리 트래픽이 함께 흐르지만, 쿠팡/Akamai가 보는
  발신 IP는 각각 다르다(집 IP vs Decodo 출구들). NAT 공유 자체의 간섭은
  이론상 없으며(§2.1 9/29 실측과 정합), A와 B/C의 동시 운영은 허용한다.

### 3.2 회선·세션 정책 (B/C)

1. **인스턴스별 고정 sid.** `user-<계정>-session-b01-sessionduration-1440-country-kr`
   형식을 매 실행 동일하게 쓴다. 이유:
   - 병렬 확대의 목적은 회선 평판을 인스턴스에 **축적**해 안정 궤도를 만드는
     것 — 시도마다 sid를 갱신하는 메인 앱 방식은 차단 회피 중심이고, 급속
     순환은 §2.2의 차단 패턴과 상관 있었다.
   - 회전(무세션)은 절대 금지(§2.3).
2. **매 실행 출구 IP 로깅.** 파이프라인 시작 시 `fetch_exit_ip()` 1회 →
   결과를 `top_pipeline_runs.jsonl`에 기록(비밀번호 마스킹, IP만).
   - 목적: (a) B≠C 출구 IP 상이성 확인(ASN까지 눈으로 비교),
     (b) 24시간 세션 만료 시 IP 교체 거동 실측(§10.1),
     (c) 풀 차단 해석 자료.
3. **차단 시 회선 교체 금지, 인스턴스 비활성.** 차단 감지 시 현행대로 해당
   인스턴스 예약만 자동 비활성화. **당일 sid 교체·재시도 금지**(0/8 실측).
   재개는 다음 날 사전점검(아래 4) 통과 후.
4. **익일 사전점검.** 비활성화된 인스턴스의 재등록 전에 브라우저 없이
   해당 회선으로 쿠팡 홈 GET 1회(requests + Chrome 계열 헤더; 메인 워크트리
   `env_probe.py` 방식). 403이면 그날은 그 인스턴스를 쉰다. A(집 회선)의
   사전점검은 A 회선으로 1회 — **다른 인스턴스 회선으로 점검하지 않는다.**
5. **프로필 연속성.** 고정 sid로 IP가 24시간 주기로 갈리더라도 프로필(쿠키)은
   유지한다. 일상적 DHCP 재할당과 같은 하루 1회 이하 교체는 수용하고,
   **요청 단위 IP 변화만 금지**한다(§2.3 쿠키-IP 불일치 근거). 만료 거동은
   §10.1에서 실측 확정 전까지 가설로 둔다.

## 4. 예약 설계 (Windows 작업 스케줄러)

- 작업당 구조는 현행 그대로: `register_*.ps1`(트리거 등록) → 예약 시각에
  `run_*.ps1` → `coupang_patchright_top_pipeline.py` 1회 실행 → 종료 코드에
  따라 작업 비활성(20/21/22/23/503 재시도 외 0 아님 → 비활성, 30 → 완성형
  복사 후 비활성).
- 인스턴스별 파라미터: 작업명·출력 폴더·장부 루트·세션 ID·첫 실행 시각.
  실행기/등록기 스크립트가 이 값을 받도록 파라미터화한다(§5.6).
- 작업당 일회성 트리거 상한 48개(실측)는 유지: 80분 간격 일 18회 × 인스턴스
  이므로 여유. 상한 도달 시 기존 방식(이어서 재등록)으로 연장.
- `MultipleInstances IgnoreNew`은 작업 단위로 적용되므로 인스턴스 간에는
  무관하다. 한 인스턴스의 중복 실행은 여전히 막힌다.
- **주의(미확인 §10.4):** headed Chrome + `LogonType Interactive`는 화면이
  잠기거나 RDP 세션이 끊기면 동작이 바뀔 수 있다. 현재 A는 무인 80분 예약으로
  무차단 운영 중이므로 실질 문제는 없었던 것으로 보이나, B 등록 전 1회
  잠금 화면 상태에서의 동작을 확인한다.

## 5. 코드 변경 목록 (구현 착수 시)

파라미터화다. 모두 오프라인 테스트로 검증 가능하다.

   자격증명은 기존대로 `output/decodo_settings.json`(.gitignore).

   전달. (유일한 코어 변경. 판매자 API는 `page.evaluate(fetch…)`로 브라우저
   안에서 나가므로 컨텍스트 프록시 하나로 목록+판매자 전부 커버된다.)
3. **`app/core/coupang/patchright_top_thousand.py`,
   `patchright_top_sellers.py`** — 실행 함수에 `proxy: dict | None = None`
   파라미터 추가 → `factory(user_data_dir, headless=False, proxy=proxy)`.
   브라우저 팩토리 주입 구조(`browser_scope_factory`)는 이미 있으므로
   통과만 시킨다.
4. **CLI(`scripts/prototypes/coupang_patchright_top_thousand.py`,
   `coupang_patchright_top_sellers.py`)** — `--proxy-session-id`(선택) 추가.
   값이 있으면 `sticky_proxy_dict(load_settings(), sid)`로 조립해 코어에
   전달. 자격 미완비면 시작 전 거부(브라우저 열기 전).
5. **`scripts/prototypes/coupang_patchright_top_pipeline.py`** —
   `--proxy-session-id` 통과 + 실행 시작 시 `fetch_exit_ip()` 1회 결과를
   실행 로그에 기록(실패 시 경고만, 수집 중단 아님 — 점검 엔드포인트 불능은
   회선 불능과 다르다).
6. **PowerShell 파라미터화** — `run_patchright_top1000.ps1`,
   `register_patchright_top1000_schedule.ps1`에
   `TaskName/OutputDir/StateRoot/SessionId` 파라미터 추가(기본값 = 현행 A값).
   인스턴스 등록은 같은 스크립트 재사용.
7. **통합 점검 스크립트(신규, 읽기 전용)** — `patchright_instances_status.ps1`:
   A/B/C의 `canary_guard.json`(blocked/마지막 실접속/일일 예약), 파이프라인
   실행 로그 마지막 줄, 예약 작업 상태를 한 번에 출력. 네트워크 요청 0회.
8. **오프라인 테스트** (`tests/`, 현행 패턴 준수):
   - 프록시 dict 조립: sid 고정 문자열 → 사용자명 형식 검증, 자격 미완비 거부
   - 패키징: CLI `--proxy-session-id` → 코어 실행 함수 → 가짜 브라우저
     팩토리가 받은 인자에 proxy dict 포함(목록·판매자 양쪽)
   - `patchright_browser` 서명: 키워드 인자 호환(기존 호출처는 proxy 없이
     동작 유지 — A 회귀 방지)
   - 파이프라인: 출구 IP 로깅 성공/실패 두 갈래(실패해도 종료 코드 0)
   - 실행기 파라미터: PowerShell 구문 검사

A(프록시 없음)는 모든 변경 뒤에도 동일하게 동작해야 한다 — `proxy=None`이
현행과 같은 호출 경로가 되도록 하는 것이 호환 조건이다.

## 6. 트래픽·비용 설계

- 실측 기준(메인 앱, 2026-09): 카테고리 1개(목록 10~19페이지 + 판매자
  전체) ≈ **0.1~0.15GB**. 목록 HTML이 대부분이고 판매자 API는 경량.
- B 1개 가족(상위+하위 약 8~10카테고리) 완주 ≈ **1~1.5GB**.
- 현행 플랜: $4/GB · 4GB(9/28 기준 3.3GB 사용). **B/C 추가 시 트래픽이
  즉시 병목**이므로:
  1. B 첫 가족은 소규모(하위 2~3카테고리)로 시작해 실측 후 조정.
  2. 플랜 상향 여부는 §10.3 결정 사항.
  3. 한도 소진 시 `fetch_exit_ip`가 이미 "사용량 소진(407)"으로 분류해
     안내하므로(복사한 decodo.py에 구현됨) 폭주는 없다. 주 1회 대시보드
     육성 확인을 운영 점검 항목에 추가.
- A(집 회선)는 Decodo 트래픽을 쓰지 않는다.

## 7. 안전 규칙

### 7.1 인스턴스 격리 (현행 규칙의 인스턴스별 적용)

- 차단 신호 1회(Access Denied, Edgesuite 참조번호, CAPTCHA, 403/418/429,
  한국어 제한 문구) → **그 인스턴스만** 잠금 + 예약 비활성.
- HTTP 503 → 3시간 뒤 1회 재시도(현행 규칙 동일).
- 차단 당일 sid 교체·재시도 금지(§3.2-3). 재개는 익일 사전점검 후.
- 한 인스턴스의 ledger에 기록되는 모든 상한(최소 60분 간격, 세션 600개,
  일일 예약 등)은 인스턴스별로 독립 계산 — 전역 합산을 하지 않는다.
  회선이 다르므로 합산 근거가 없다(§2.1).

### 7.2 전역 정지 조건 (지문 상관 감지)

회선이 다른 인스턴스들이 **같은 6시간 창 안에 함께 차단**되면, 회선 축으로
설명되지 않으므로 지문/행동 패턴 상관 감지 가능성을 우선한다. 이 경우:

1. 전 인스턴스 예약 비활성(수동).
2. 두 인스턴스의 차단 참조번호·시각·직전 세션 규모를 비교 기록.
3. 원인 평가 전 재개 금지. 평가 결과를 이 문서에 추가.
   - 1회 발생: 우연일 수 있으나 재개는 인스턴스별 24시간 이상 엇갈려서.
   - 2회 발생: 병렬 확장 철회 후 단일 인스턴스로 회귀(지문 상관이 사실상
     확정된 것으로 본다).

### 7.3 운영 규율 (병렬화로 인해 새로 강조)

- 실수집 중 **어떤 회선에서든** 별도 진단 트래픽 금지(9/27 밤 사고 재발
  방지). 사전점검은 §3.2-4의 인스턴스 자기 회선 1회만.
- 폰 등 같은 집 와이파이 기기의 쿠팡 사용 자제 안내는 기존 유지(LTE 무관).
- B/C의 출구 IP가 우연히 같아지는지 주간 점검(`fetch_exit_ip` 로그 비교).
  같으면 한쪽 sid를 교체(차단 상황이 아니어도, 사전 예방 목적은 허용).

## 8. 단계별 실증 계획

### Phase 0 — 구현·오프라인 검증 (§5 전체)

완료 기준: 신규 오프라인 테스트 전부 통과 + 기존 patchright 관련 테스트
회귀 없음 + A 구성(프록시 없음)이 변경 전과 동일한 명령으로 동작.

### Phase 1 — 인스턴스 B 카나리 (24시간, A 계속 운영)

- B: 소규모 신규 가족(하위 2~3카테고리), Decodo `sid=b01`, +40분 오프셋,
  80분 간격 예약 18회.
- 성공 기준(전부 충족):
  1. B 브라우저 차단 0건, 503 ≤ 1회(3시간 재시도 포함 정상 종료)
  2. A의 세션 성공률·차단 지표가 B 추가 전후 동일 (A 간섭 없음 확인)
  3. 출구 IP 로그: 24시간 내 동일(또는 만료 교체 1회 기록)
  4. 트래픽 실측이 §6 견적 범위 내
- 실패 시: §3.2-3 규칙대로 B만 비활성. 풀 차단 양상이면 §2.2 관측으로
  기록하고 48시간 후 재시도 1회 — 재차 풀 차단이면 B/C 확장 철회 논의.

### Phase 2 — 인스턴스 C 추가 (48시간 관찰)

- B 24시간 무차단 후 C 추가(`sid=c01`, +53분 오프셋, 다른 가족).
- 추가 확인: B≠C 출구 IP·ASN 상이, 나머지는 Phase 1과 동일 기준.

### Phase 3 — 상시 운영

- 통합 점검 스크립트로 일일 확인(§5.7). 주간: 트래픽 대시보드, 출구 IP
  다양성, 전역 정지 조건 부재 점검.
- 각 인스턴스는 가족 완주 시 종료 코드 30으로 자동 완결 → 다음 가족을
  새 인스턴스 파라미터로 재등록.

## 10. 미해결 결정 사항

1. **세션 만료 거동(§3.2-5).** `sessionduration-1440` 고정 sid가 만료 경계에서
   같은 sid로 새 IP를 받는지, 세션 자체가 거부되는지 — B 카나리 24시간
   로그로 실측 후 이 문서에 기록. 거부된다면 sid에 일자 접미(`b01-1002`)를
   붙인 계획적 일 갱신으로 전환.
2. **B/C 담당 카테고리 가족 선택.** 현행 견과/건과+축산은 A가 마무리.
   B/C의 가족은 사용자 결정 사항(추천: B는 소규모 가족으로 카나리 겸용).
3. **Decodo 플랜 상향 여부.** Phase 1 트래픽 실측 후 판단.
4. **잠금 화면/RDP 종료 시 headed Chrome 동작.** B 등록 전 1회 실측.
   문제가 있으면 예약 시각대 화면 유지 or headless 전환 평가(단 headless는
   지문 변화로 신규 리스크 — 기본값은 headed 유지).

## 11. 착수 조건과 순서

1. **전제: 진행 중인 판매자 완성형 단계(메인 작업)가 안정 궤도에 오른 뒤
   착수** — 핸드오프 §10 권고를 유지한다. 병렬 확장은 현재 캠페인 완결 후의
   다음 캠페인부터 적용하는 것이 원칙. (예외: A가 완성형 종료 코드 30으로
   끝난 뒤라면 바로 Phase 0 가능.)
2. Phase 0: §5 변경 + 오프라인 테스트 (첫 PR 단위: §5.1~5.2 + 테스트)
3. Phase 1: B 등록 → 24시간 카나리 → 본 문서 §10 항목 기록
4. Phase 2~3: C 추가 및 상시 운영 전환
