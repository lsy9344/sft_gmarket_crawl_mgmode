## 1. 현재 동작과 변경 이유

- 앱은 목록에 Decodo 한국 스티키 회선을 쓰고, 판매자 정보에는 이 PC 회선을 쓴다. 실패하면 최대 3번 새 Decodo 세션으로 다시 시도하지만, 매 시도마다 목록 1페이지부터 시작한다 (`app/core/coupang/decodo_run.py`, `app/core/coupang/search_crawler.py`).
- 목록 상품은 수집 중 메모리의 `products`에만 있다. 목록 단계에서 실패하면 `summary.records`가 비어 있어 상품 목록은 결과 파일로 저장되지 않는다 (`app/core/coupang/search_crawler.py`, `app/core/coupang/crawler.py`).
- 히스토리의 `runner_state.json`은 **완료한 카테고리를 건너뛰는 기록**이다. 같은 카테고리의 페이지나 판매자 위치를 기억하는 기능은 아니다 (`DECODO_PROXY_METHODOLOGY_20260910.md` §3·§4·§5, `HANDOFF_COUPANG_COLD_FROZEN_20260911.md` §9).
- 이 문서는 과거 `/np/omp` 통합을 다룬 `WORK_ORDER.md`의 수집 경로 설명보다 **현재 카테고리 엔진과 Decodo 실측 기록**을 우선한다.

## 2. 완료 조건

1. 16페이지를 읽는 도중 회선이 끊기면, 1~15페이지에서 얻은 상품은 디스크에 남는다. 새 한국 회선으로 홈 웜업을 거친 뒤 경계 페이지를 다시 확인하고 16페이지부터 수집한다.
2. 앱을 닫았다 다시 열어도 같은 카테고리·출력 폴더를 선택하면 미완료 작업을 찾고 이어서 진행한다. 취소도 진행 기록을 보존한다.
3. 같은 상품과 판매자는 재시작 횟수와 관계없이 결과에 한 번만 나온다. 판매자 정보 단계가 끊겨도 확인된 판매자 결과는 남고 미확인 판매자부터 다시 처리한다.
4. 저장 실패·손상·설정 불일치는 조용히 건너뛰지 않는다. 재개를 멈추고 화면에 이유를 보여 준다.
5. 기존의 빈 페이지 **연속 2회** 종료 판정, 200페이지 상한, `일부 수집` 결과명과 기록, 카테고리별 폴더, 3회 회선 재시도는 유지한다. 재개 과정에서 목록 누락 여부를 증명할 수 없으면 `완료`로 표시하지 않는다.

## 3. 구현 지시

### 3.1 저장 위치와 단위

- 카테고리 하위 폴더에 전용 진행 파일 하나를 둔다. 페이지와 판매자마다 작은 거래로 저장할 수 있도록 Python 표준 라이브러리의 SQLite를 사용한다. 진행 파일을 최종 JSON/CSV와 구분하고, 프록시 비밀번호·쿠키·브라우저 프로필 내용은 넣지 않는다.
- 첫 실행 시 진행 기록에 형식 버전, 카테고리 ID, 카테고리 전용 모드, 로켓 제외 여부, 최대 페이지, 출력 위치, 실행 상태를 넣는다. 재개 시 이 값들이 현재 선택과 일치하는지 검사한다. 이름 표시만 바뀐 경우에는 카테고리 ID를 기준으로 판단한다.
- 기존 출력 폴더 잠금을 재개 파일에도 적용한다. 다른 앱 창이 같은 폴더를 동시에 수집하게 두지 않는다 (`app/core/storage.py:43`).
- DB 쓰기에 실패하거나 내용을 해석할 수 없으면 그 페이지·판매자를 `완료`로 기록하지 않는다. 진행 파일을 임의로 삭제하거나 새 실행으로 덮어쓰지 않는다.

### 3.2 목록 페이지

- 정상적으로 상품을 읽은 **한 페이지가 끝난 뒤**, 새 상품(`SearchProduct`의 중복 키와 판매자 매핑에 필요한 `vendorItemId` 포함), 마지막 완료 페이지, 빈 페이지 연속 횟수, 로켓 제외 집계를 **한 거래**로 저장한다. 거래가 끝나기 전에는 다음 페이지로 넘어가지 않는다.
- 차단·로드 실패·브라우저 종료가 발생한 페이지는 완료 표시하지 않는다. 새 Decodo 스티키 세션의 실제 한국 출발을 확인하고 홈 웜업한 뒤, 저장된 마지막 페이지를 경계 확인용으로 다시 읽어 상품 ID로 중복을 제거하고 미완료 페이지로 간다. 첫 페이지 홈 메뉴 진입 규칙은 유지한다.
- 첫 빈 페이지가 저장된 뒤 세션이 바뀌면 그 빈 페이지를 새 회선에서 다시 확인한다. 새 세션에서 유효한 빈 페이지 2회 연속이 관찰되기 전에는 목록 끝으로 보지 않는다. 셸·차단·추출 오류를 빈 페이지로 확정하지 않는다.
- 200페이지에서 두 번째 연속 빈 페이지를 확인하지 못하면 기존과 같이 `일부 수집`으로 남긴다. 페이지 번호가 재개 중 바뀌거나 저장한 경계 페이지의 상품 집합이 크게 달라지면 목록 변동을 로그에 남기고, 누락 여부를 확인하지 못한 실행은 `완료`로 채택하지 않는다. 페이지 번호만으로 **모든 상품 수집**을 보장한다고 안내하지 않는다.

### 3.3 판매자 매핑·사업자정보

- 목록 단계가 끝나면 `상품 목록 확보` 상태를 먼저 저장한다. 이후 회선 전환이나 판매자 API가 실패해도 Decodo 목록을 다시 읽지 않는다.
- `individualInfo/products` 매핑이 끝났을 때 판매자 ID와 대표 상품 연결 정보를 저장한다. 매핑 도중 실패했다면 매핑만 처음부터 다시 수행한다. 이 API는 이 PC 회선을 쓰므로 Decodo IP를 바꿔도 이 단계의 차단은 해결되지 않는다는 점을 실패 원인에 반영한다.
- `getStoreReview`에서는 판매자별로 정상 사업자정보 레코드 또는 정상 브랜드 판매자 판정을 저장한다. 오류·타임아웃을 성공이나 브랜드 판매자로 기록하지 않고 재개 대상에 남긴다. 재시작 후 저장된 판매자를 건너뛰고 남은 판매자를 처리한다. 최종 JSON/CSV는 판매자 ID로 중복 제거한 저장 결과에서 생성한다.
- 이 PC 회선의 판매자 API가 연속 실패한 경우 기존 중단·쿨다운 규칙을 유지한다. 이 사유로 Decodo 세션을 불필요하게 바꾸고 목록 단계까지 되돌리지 않는다. 미확인 판매자가 남아 있으면 성공으로 표시하지 않는다.

### 3.4 재시도·화면·결과

- 현재 `run_category_attempts`의 최대 3회, 한국 회선 확인, 90초 대기와 취소 가능 대기는 유지한다. 새 시도에는 저장된 진행 상태를 넘기고, 시도별 브라우저 프로필과 진단 파일은 계속 분리한다.
- 시작 전에 같은 카테고리 폴더에 미완료 기록이 있으면 화면·로그에 `이어서 수집: 마지막 확인 페이지 N / 상품 M개 / 확인된 판매자 K명`을 보여 준다. 최종 파일을 열 때 이전 시도의 일부 파일이 아닌 **현재 진행 기록에서 만든 최신 결과**를 연다.
- 사용자가 의도적으로 처음부터 새로 수집할 수 있도록 `처음부터 다시 수집`을 명시적인 동작으로 제공한다. 기존 진행 파일과 결과 파일을 자동 삭제하지 말고, 새 실행 파일로 보관한 뒤 새 진행 상태를 만든다. 같은 폴더에서 아무 안내 없이 기존 기록을 섞거나 덮어쓰지 않는다.
- 재개 실행에서 마지막 빈 페이지 2회를 확인해도, 이전 페이지들의 상품 순서 변동으로 누락이 없음을 확인하지 못했다면 `일부 수집(재개·목록 변동 미확인)`으로 저장·표시·실행 기록에 남긴다. `완료`는 끊김 없는 전체 목록 확인 또는 동등한 전체 확인을 마친 경우에만 사용한다. 이 판정은 `should_keep_attempt`에도 일관되게 반영한다.

## 5. 시험 및 채택 기준

실제 Coupang·Decodo 연결 없이 가짜 페이지/API로 아래 동작을 검증한다.

1. 페이지 1~15 저장 후 16페이지 차단 → 새 회선 시도에서 1페이지부터 다시 읽지 않고 15페이지 경계를 확인한 뒤 16페이지를 수집한다. 상품은 중복 없이 합쳐진다.
2. 페이지를 읽었지만 저장 전에 실패 → 해당 페이지는 미완료이고 다시 읽는다. 반대로 저장 후 종료 → 저장한 상품과 페이지가 재시작 뒤 남는다.
3. 첫 빈 페이지 직후 종료 → 새 회선에서 다시 확인하며, 빈 페이지 2회가 확정되지 않으면 `완료`가 아니다. 200페이지 경계의 `일부 수집` 판정도 유지한다.
4. 판매자 매핑 또는 57번째 판매자 정보 수집 중 실패 → 목록은 다시 읽지 않고, 저장된 레코드는 유지하며 미완료 판매자만 재처리한다. 오류 판매자는 완료 집계에 들어가지 않는다.
5. 앱 재시작·취소·3회 재시도 소진·설정 불일치·진행 파일 손상·쓰기 실패·두 창의 같은 폴더 사용을 각각 검증한다. 기존 Coupang/Gmarket 관련 시험을 통과시킨다.
6. 재개 뒤 목록 변동이 감지되거나 전체 페이지의 누락 여부를 확인하지 못하면 파일명, 화면, 실행 기록 어디에도 `성공` 또는 `완료`라고 쓰지 않는다.

## 6. 운영상 남는 한계

- 쿠팡 목록의 상품 순서가 실행 사이에 바뀌면 페이지 커서와 중복 제거만으로 상품 누락을 완전히 증명할 수 없다. 재개 결과의 보수적인 상태 표시가 필요하다.
- 특정 vendorItemId 가 영구히 매핑되지 않으면(예: 목록 저장 뒤 상품이 삭제되어 개별정보 API 가 응답하지 않음) 재시작할 때마다 매핑이 같은 지점에서 실패해 회선 교체 3회가 반복되고, 누락 증명이 남아 있는 한 그 카테고리는 `완료`로 봉인되지 않는다. 유일한 탈출은 '처음부터 다시 수집'이다 — 누락을 조용히 확정하는 것보다 나은 보수적 판정의 의도된 귀결이지만, 재개 기간이 길어진 실행에서 이 시나리오가 반복되면 삭제된 상품을 의심한다.
- 현재 앱에는 브라우저 호출이 **아무 응답 없이 멈춘 경우(F9)** 자동으로 끊는 감시가 없다. 이 작업은 오류·종료 뒤 재개를 구현하며, 무한 대기의 자동 감지·안전한 강제 중단은 별도 작업으로 다룬다. 감시가 구현되기 전에는 `모든 멈춤 자동 복구`라고 안내하지 않는다.
- 실제 Decodo 회선과 큰 카테고리에서는 재개가 시간·트래픽을 얼마나 줄이는지 별도 실측이 필요하다. 기본 자동 시험은 네트워크를 사용하지 않는다.
