# Patchright 과일 전량 수집 전환 계획

작성일: 2026-09-01  
대상: 현재 Patchright 과일 수집 작업을 이어받는 에이전트  
관련 문서: `docs/coupang/PATCHRIGHT_EXPERIMENT_REPORT.md`

## 1. 결론

초기 `12개 수집 → 30분 대기` 방식과 여러 카테고리를 한 번에 잇는 방식은 모두
폐기한다. 10페이지 실행은 HTTP 200이었지만 약 20페이지를 이어간 실행에서 HTTP
403이 발생했기 때문이다. 단일 원인이 증명된 것은 아니므로 세션 크기, 하루 누계와
간격을 함께 제한한다.

현재 운영 봉투는 한 세션 최대 10페이지·600개, 최근 24시간 최대 46페이지·2,460개,
하루 최대 8세션이다. 현재 간격 시험에서는 세션 사이 최소 2시간이다. 한 세션은
카테고리 경계를 넘지 않는다. 상품 목록과
판매자정보 수집도 계속 분리한다.

이 문서의 목표는 다음 두 가지를 함께 만족하는 것이다.

1. 과일 카테고리에 공개된 상품 목록을 가능한 범위까지 모두 기록한다.
2. 상품에서 발견한 판매자를 전체 카테고리 기준으로 중복 제거한 뒤, 공개
   사업자정보를 판매자당 한 번만 저장한다.

결과는 완료가 아닌 부분 수집이다.

## 3. 현재 방식의 문제

현재 방식은 작은 상품 묶음마다 홈, 카테고리, 상점 세션 페이지를 다시 연다. 상품
12개마다 같은 준비 작업을 반복하므로 전체 요청 수와 시간이 불필요하게 커진다.

또한 현재 결과의 중심은 판매자 사업자정보다. 상품 수천~수만 건 자체를 최종
결과로 남기려면 상품 파일과 상품-판매자 연결 파일이 별도로 필요하다.

현재의 고정 경계도 전량 완료 판정에 부족하다.

- 카테고리당 50페이지에 도달했다는 이유만으로 완료 처리하면 안 된다.
- 50페이지에서도 상품이 계속 나오면 `미완료: 안전 상한 도달`로 기록해야 한다.
- 페이지당 60개가 실제 페이지의 전부인지 실측으로 확인해야 한다.
- 목록은 시간, 품절, 광고, 개인화에 따라 바뀔 수 있으므로 브라우저 수집만으로
  쿠팡 전체 상품의 영구적인 100% 완전성을 증명할 수는 없다.

## 4. 목표 구조

수집을 두 단계로 나눈다.

### 4.1 1단계: 상품 목록 수집

과일 하위 카테고리 12개를 차례로 방문한다. 한 페이지에서 보이는 상품 링크를 한
번에 읽고 다음 항목을 먼저 저장한다.

- 카테고리 ID와 이름
- 페이지 번호
- 상품 ID
- item ID
- vendorItemId
- 상품명
- 가격
- 상품 URL
- 수집 시각

상품 목록 단계에서는 상품마다 판매자 사업자정보를 요청하지 않는다. 페이지 단위로
위치를 저장하고, 중단되면 마지막으로 완료한 페이지 다음부터 이어간다.

### 4.2 2단계: 판매자 연결과 사업자정보 수집

목록에서 모은 `vendorItemId`를 판매자 ID로 연결한다. 같은 판매자가 여러 상품과
여러 카테고리에 나타나도 판매자정보는 한 번만 요청한다.

판매자정보 요청 결과는 다음 셋으로 구분해 기록한다.

- `saved`: 공개 사업자정보 저장 완료
- `no_public_info`: 공개 이름 또는 표준 사업자정보가 없음
- `failed`: 응답 오류로 완료하지 못함

`failed`는 완료로 세지 않는다. 재개할 수 있도록 별도 대기 목록에 남긴다. 자동으로
짧게 반복 요청하지 않는다.

## 5. 최종 결과 파일

최종 결과는 최소 세 파일로 나눈다.

```text
fruit_products.csv
fruit_sellers.csv
fruit_product_seller.csv
```

- `fruit_products.csv`: 수집한 고유 상품 전체
- `fruit_sellers.csv`: 중복 없는 판매자 사업자정보
- `fruit_product_seller.csv`: 상품과 판매자 연결 관계

작업 상태와 검증 자료도 남긴다.

```text
fruit_collection_state.json
fruit_failed_sellers.json
fruit_collection_summary.json
SHA256SUMS.txt
```

기존 `patchright_sample_*.json/csv`는 실험 증거로 보존한다. 새 전량 수집기가 이를
덮어쓰거나 삭제하면 안 된다.

현재 간격 시험에서는 모든 실접속 사이에 최소 2시간을 강제한다. 한국 날짜 기준
하루 최대 8세션을 마지막 안전문으로 두고, 날짜가 바뀌어도 최근 24시간 최대
46페이지·2,460개를 넘지 못하게 한다. 각 세션은 예정 페이지와 상품 수를 먼저
예약하고 정상 종료 때 사용하지 않은 양만 돌려놓는다. 기존 하루 2,460개 안전문도
함께 유지한다.

전량 모드에서는 한 브라우저 실행 안에서 현재 카테고리의 페이지만 최대 10페이지,
상품 최대 600개까지 처리한다. 세션 봉투에 도달하면 작업 전체 실패가 아닌
`listing_session_limit_reached`로 저장하고 다음 세션에서 이어간다. 페이지 사이는
고정 15초를 기다리고 카테고리 끝에서는 반드시 브라우저를 닫는다. 여러 카테고리를
한 실행에서 잇는 방식은 실제 403이 발생해 사용하지 않는다.

차단 쿠키 삭제, 세션별 새 프로필, 무작위 행동 지연은 적용하지 않는다. 이는 관찰된
원인을 분리해 검증하지 못하며 차단 판단 회피로 이어질 수 있다. 같은 감사 가능한
프로필, 고정 간격, 프록시 없는 연결을 유지한다.

## 7. 차단과 오류 규칙

다음 중 하나가 보이면 즉시 전체 실행을 멈춘다.

- `Access Denied`
- `errors.edgesuite.net` 또는 Reference 번호
- CAPTCHA
- HTTP 403, 418, 429
- 한국어 접근 제한 문구

차단 때 지켜야 할 순서는 다음과 같다.

1. 현재까지 완료된 상품·판매자·위치를 안전하게 저장한다.
2. 공통 안전 기록을 `blocked`로 잠근다.
3. 같은 엔진이나 다른 엔진으로 즉시 다시 시도하지 않는다.
4. 차단 위치, 상태 코드, 참조번호와 마지막 성공 위치를 보고서에 기록한다.

일반 네트워크 오류도 짧게 무한 반복하지 않는다. 실패 항목을 대기 목록에 남기고
현재 실행을 안전하게 끝낸다.

## 8. 완료 판정

하위 카테고리 하나는 다음 조건을 모두 만족해야 완료다.

- 페이지를 순서대로 처리했다.
- 정상 상품이 있는 마지막 페이지 뒤에서 빈 페이지 종료 조건을 확인했다.
- 안전 상한에 도달했다면 완료가 아니라 `incomplete_limit_reached`로 기록했다.
- 모든 상품 ID와 vendorItemId가 파일에 저장됐다.
- 상품 중복 제거 전후 개수가 요약 파일에 기록됐다.

과일 전체는 다음 조건을 모두 만족해야 완료다.

- 로컬 트리의 과일 하위 카테고리 12개가 모두 완료 상태다.
- 상품 파일, 판매자 파일, 상품-판매자 연결 파일이 만들어졌다.
- 고유 상품 수와 고유 판매자 수가 다시 계산한 값과 같다.
- 모든 판매자는 `saved`, `no_public_info`, `failed` 중 하나의 상태를 가진다.
- `failed`가 한 건이라도 있으면 `완전 성공`으로 표시하지 않는다.
- JSON/CSV를 다시 읽을 수 있고 필수 열이 존재한다.
- 모든 결과 파일의 SHA-256 해시를 저장하고 검증한다.
- 실행 뒤 Patchright 전용 Chrome 프로세스가 남지 않는다.

## 9. 예상 시간

사이트가 계속 정상 응답하고 페이지 수가 현재 가정 범위 안에 있을 때의 예상이다.

- 전량 수집기 변경과 네트워크 없는 테스트: 약 1~2시간
- 24개 → 60개 → 3페이지 → 10페이지 실접속 검증: 약 1~3시간
- 과일 상품 목록 전체: 약 4~7일
- 고유 판매자 사업자정보: 약 2~12시간
- 중복·누락·파일 검증: 약 1시간

남은 목록을 150~200페이지로 보는 가정과 새 상한을 함께 적용하면 상품 목록만 약
4~7일이 걸릴 수 있다. 이는 계획용 추정이며 실제 페이지 수, 차단, 목록 변화,
판매자 수 또는 빈 페이지 판정에 따라 더 오래 걸린다. 완료 시각을 보장하면 안 된다.

## 10. 현재 에이전트가 바로 할 일

1. 2026-09-02 18:14:10에 최대 8페이지·480개 안에서 상품 목록을 이어간다.
2. 앞 단계가 성공한 경우에만 다음 예약을 실행한다.
3. 예약 등록 전에 결과와 안전 기록을 별도 폴더에 백업한다.
4. 차단·오류·예상 밖 결과가 한 번이라도 나오면 뒤 단계는 브라우저를 열지 않는다.
5. 18:14 작업은 오늘 8번째 세션으로 실행한다.
6. 가격 확인 필요 1건은 신뢰할 수 있는 값이 확인되기 전까지 임의 보정하지 않는다.
7. 이 검증이 끝나도 과일 전량 수집을 자동으로 시작하지 않는다.

## 11. 구현 시 지켜야 할 경계

- 기존 Camoufox 수집 엔진을 함께 바꾸지 않는다.
- 기존 실험 결과, 백업과 안전 기록을 삭제하거나 초기화하지 않는다.
- 현재 성공 위치를 임의로 앞으로 이동시키지 않는다.
- 테스트 실패 상태에서 실제 접속을 실행하지 않는다.
- 사이트가 계속 상품을 반환하는데 페이지 상한만으로 완료 처리하지 않는다.
- 화면에서 차단이 보이지 않았다는 사실을 "탐지되지 않음"으로 표현하지 않는다.
