### D5. 재현성 검증 (사용자 질문: "다음 날 또 막히지 않나?")

| 실험 | 목적 | 결과 |
|---|---|---|
| 1.5시간 후 **새 세션** | 시간 경과 영향 | ❌ 셸 |
| **성공 세션의 프로필 재사용** | 쿠키/지문 가치 | ❌ 셸 — 프로필만으로 불충분 |
| **무세션(회전) 3회** | 기본 모드 확인 | ❌ IP가 매 요청 변경(네팔·파키스탄·캄보디아) → 셸 |
| **스티키 세션 6회 로테이션** | IP 품질 분포 | ⭕ 403(플래그 IP) 3개 / **200 정상 1개** / 나머지 셸 |

1. **회전 프록시가 근본 문제** — 쿠키는 같은데 IP가 요청마다 바뀌면 Akamai가

2. **curl은 진단 도구로 부적합** — Akamai가 curl을 브라우저와 다르게 취급.
   판정은 반드시 Camoufox로.

  → 브라우저 PID만 SIGTERM → 러너가 즉시 실패 감지(`products=467 term=error (7094초)`)
  → 90초 후 **시도 2 자동 시작** (새 세션 r22157298).

#### 감시견 구현 시 함정 (2026-09-11 실측 — 오탐 사례)

감시견 v1(40분 경과+CPU 정지)은 정지를 최대 40분 방치 → v2 는 "6분 경과 +
75초 간격 4회 연속 CPU 무변화"로 앞당겼다. 그런데 **오탐 1건 발생**:

- 증상: 정상 진행 중이던 시도(13페이지까지 순조)를 "CPU 0 정지"로 오판해
  브라우저를 종료시킴(그 시도는 products=0 으로 실패 처리).
- 원인: 러너는 `xvfb-run` 래퍼로 실행되어 **프로세스가 2개**다 —
  `/bin/sh /usr/bin/xvfb-run -a .../.venv/bin/python scripts/...py` (래퍼, CPU 0)
  와 실제 `python` 프로세스(CPU 누적). 문자열 매칭(`"/.venv/bin/python" in line`)은
  **래퍼 줄에도 매칭**되어 CPU 가 영원히 0 인 래퍼를 감시했다.
- 수정(v2.1): PID 선택을 `/proc/<pid>/comm` == `python*` 로 못박음.
- 교훈: 프로세스 감시 대상은 **명령문자열 매칭이 아니라 comm/cmdline 의 실행
  파일**로 확정해야 한다. 래퍼 스크립트가 있는 실행은 항상 2프로세스다.

#### 러너 재기동(재개) 절차 (실전 확인)

세션 스크래치패드가 정리되며 러너가 종료된 사례(2026-09-11 아침)에서:

7. **출력 폴더 카테고리별 분리** — blockguard 쿨다운 오염 방지 + 부분 성과 보존

10. **교차 확인은 curl 대신 ip.decodo.com/json + Camoufox 조합**

## 9. 앱 반영: 중단 지점 저장·재개 (2026-09-16 구현)

§5 과제 5의 앱 반영. 카테고리 폴더의 `resume.sqlite3`(SQLite)에 진행을 저장하고,
회선 차단·브라우저 종료·앱 재실행 뒤 같은 카테고리·폴더로 시작하면 이어서 수집한다.

- 저장 단위(작업지시서 §3 준수): 정상으로 읽은 **페이지마다 한 거래**(상품+경계+빈
  페이지 집계), 목록 완료 시 매핑 일괄, **판매자 1명당 한 거래**(사업자정보 또는
  브랜드 판매자 판정). 오류·타임아웃 판매자는 저장하지 않아 재개 대상에 남는다.
- 재개 동작: 새 회선에서 홈 웜업 뒤 저장된 **경계 페이지를 다시 확인**해 상품 ID로
  중복 제거하고 미완료 페이지부터 계속한다. 목록이 끝났던 실행은 목록·매핑을
  재요청하지 않고 미확인 판매자만 처리한다.
- 보수적 표시: 재개 결과는 경계 목록 변동(`일부 수집(재개·목록 변동 미확인)`)이나
  미확인 판매자 잔존(`일부 수집(재개·미확인 판매자)`)이 있으면 `완료`로 쓰지 않는다.
- 판매자 단계(회선 IP) 차단은 Decodo 회선 교체 대상에서 제외 — 쿨다운 뒤 재시작하면
  저장된 판매자부터 이어서 진행한다(§3.3 회선 교체 무의미 실측 반영).
- `처음부터 다시 수집`: 기존 `resume.sqlite3` 를 타임스탬프 아카이브로 보존한 뒤
  새 진행 상태로 시작한다. 결과 파일은 기존 것을 덮지 않는다(번호 자동 증가).
- 설정 불일치(로켓 제외 토글, 최대 페이지 축소) 시 재개를 중단하고 이유를 표시한다.

### 9.1 검토 반영 보강 (2026-09-16 오후 — 전체 검토에서 발견한 구멍 3건)

- **매핑 누락 봉인 방지**: 개별정보(individualInfo) 배치가 연속 한도(3회) 미만으로
  실패하면 매핑이 부분 완료된 채 파이프라인이 성공 종료할 수 있었다 — 이러면
  누락 판매자를 남긴 채 `완료` 표시 + 진행 파일 봉인으로 누락이 확정됐다.
  이제 성공 경로에서 매핑되지 않은 vendorItemId 를 확인해
  `일부 수집(매핑 누락)` 으로 표시하고 진행 기록을 열어 둔다. 재시작하면
  누락 매핑·판매자부터 이어서 처리한다.
- **완료 봉인 재실행**: 완료(FINISHED)된 카테고리를 다시 시작하면 이전에는
  대화상자 없이 저장된(구) 상품을 복원해 경계 뒤만 다시 읽는 병합 재개가
  일어났다. 이제 진행 기록을 아카이브로 보관하고 새 실행으로 시작한다
  (로그에 보관 파일명 표시).
- **진행 기록 쓰기 실패 즉시 중단**: 쓰기 실패가 `error` 로 일반화돼 회선을
  바꿔 최대 3번 재시도(전부 같은 지점 실패)했었다. 이제
  `resume_store_error` 사유로 구조화해 재시도 없이 즉시 중단한다.
