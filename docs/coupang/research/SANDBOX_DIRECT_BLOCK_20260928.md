차단 Reference: `18.c5023517.1790524219.13d45c38`. 저장됐다고 로그에 표시된 HTML은 `라면_파스타_면_432572/blocked_home_warmup_20260928_005021.html`이다. 이번 회수에서는 HTML 원문·resume DB를 추가로 열지는 않았다.

**확인된 직접 원인은 판매자 조회용 새 직접 세션에 대한 쿠팡 홈의 접근 거부다.** 앞선 23:58 사건과 같은 단계에서 발생했다. Decodo 목록 단계는 완료됐고, 이번 카테고리의 판매자 API를 요청하기 전 멈췄다. 현재 상태는 **6/13개 완료, 7번째 목록 39개 수집 후 중단**이다.

코드와 실행 로그를 대조하면, 성공했던 직접 세션의 접속 상태를 다음 카테고리에서 재사용하지 않는다. `decodo_run.py`는 매 시도마다 난수 이름의 프로필 폴더를 만들고 종료 시 정리한다. `crawler.py`는 그 폴더 안의 `proxy`와 `direct`를 분리한다. 실제 로그에도 성공한 6번째와 실패한 7번째의 직접 프로필 경로가 서로 다르게 남았다. 따라서 매 카테고리의 판매자 단계에서 새 접속 상태로 홈부터 다시 시작한다. **이 구조가 차단에 영향을 줬는지는 아직 검증되지 않았다.** 성공한 직접 세션의 재사용 여부는 후속 비교에서 확인할 후보이며, 재사용하면 반드시 해결된다는 결론은 아니다.

원인 해석의 한계:

- 이번 재발은 “39분 뒤 한 번 성공했으므로 이후에도 안정적”이라는 해석을 지지하지 않는다. 12시간이 이번 첫 재개에 필수가 아니었다는 사실과, 연속 운영이 안정적인지는 별개다.
- 이 관찰에서는 쿠팡에 추가 시험 요청을 보내지 않았다. 확인한 `/tmp/coupang-blockhunt` 및 보존 증거에 00:37~00:50 신규 시험 결과는 없었다. 하지만 파일 수정 시각만으로 다른 모든 프로그램의 접속이 없었다고 증명할 수는 없다.
- 따라서 이번 차단도 “다른 에이전트가 동시에 테스트했기 때문”으로 확정할 수 없다. 과거 요청의 영향, 앱 자체 요청, 새 세션 상태, 서버 판정 변화 중 무엇이 결정적인지는 미확인이다.
- 재발 확인 중 앱 코드나 차단 파일을 변경하지 않았고, 수집을 재시작하지 않았다.

## 최초 조사 결론 (재개 전)

**이번에는 Chromium의 직접 회선 세션이 쿠팡 홈에서 HTTP 403으로 거부됐다.** Decodo로 상품 목록을 수집하는 단계는 끝까지 성공했다. 이전 상품 연결 누락 오류도 재발하지 않았다.

바깥 시험과 샌드박스가 같은 공인 IP를 사용함을 확인했다. 따라서 서로 영향을 줄 가능성을 배제할 수 없다. 그러나 **바깥 시험 때문에 차단됐다는 인과관계는 확인되지 않았다.** 앱 자체의 수집도 같은 시간대에 진행됐고, 브라우저·세션·요청 경로도 달랐다. 요청 수만으로 어느 작업이 더 큰 원인이라고 순위를 매길 근거는 없다.

차단 후 같은 직접 회선에서 Chrome 계열을 모방한 HTTP 요청은 성공한 기록도 있다. 그러므로 공인 IP 전체가 모든 접속에서 차단됐다고 단정할 수 없다. 이 HTTP 시험은 실제 Windows Chromium 브라우저와 동일한 시험은 아니다.

## 바깥 시험과 같은 회선인가

- 바깥 시험 기록은 WSL의 직접 공인 IP를 `118.36.49.213`으로 기록한다. 바깥 Windows에서 한 앞선 비교와, 이후 WSL에서 실행한 추가 조사를 구분해야 한다.
- 이번 조사에서 WSL 직접 IP를 다시 확인했고, 9/28 00:08:11부터 실행한 샌드박스 조회에서도 **같은 `118.36.49.213`**을 확인했다.
- IP 조회는 ipify만 사용했다. 이 조사에서는 쿠팡에 새 시험 요청을 보내지 않았다.
- 이는 조사 시점의 IP 일치 증거다. 23:58:34 당시 샌드박스의 직접 공인 IP를 별도 로그로 남기지는 않았으므로, 과거 모든 요청의 출구 IP를 연속 측정한 것으로 해석하지 않는다.
- 서로 다른 브라우저 프로필이나 샌드박스를 써도 직접 공인 IP는 분리되지 않았다는 점이 확인됐다.

## 원인 판단의 범위

확인한 사실:

1. Decodo 목록 회선은 성공했다.
2. 실패는 직접 회선으로 바꾼 Chromium 세션에서 발생했다.
3. 바깥 시험과 앱의 직접 접속은 같은 공인 IP를 공유하는 환경이었다.
4. 바깥 시험과 앱 수집이 같은 시간대에 있었다.
5. 차단 후에도 같은 IP의 일부 다른 요청은 성공했다.

미확인:

- 바깥 시험이 없었으면 앱이 성공했을지
- 앱의 요청량, 바깥 시험 요청량, 세션·브라우저 차이 중 어떤 요인이 결정적이었는지
- 쿠팡/Akamai가 사용한 판정 규칙이나 점수

별도 문서 `CAMOUFOX_BLOCK_ROOT_CAUSE_20260927.md`의 구형 TLS 지문 설명은 유력한 가설을 포함하지만, 그 시험만으로 내부 판정 원인 하나가 확정된 것은 아니다. 같은 문서의 Camoufox 성공 사례와 이번 Chromium 실패까지 함께 고려해야 한다. “Chrome 계열은 항상 통과”, “Camoufox는 설정·버전 조정으로 회복 불가”를 일반적인 확정 사실로 사용하지 않는다.

## 최초 조사 당시 운영 조치

- 원인 조사 동안 실수집 회선에서 별도 차단 시험을 함께 하지 않는다. 다른 프로필·샌드박스만으로는 회선 분리가 안 되므로, 비교 실험이 필요하면 별도 인터넷 회선을 사용한다.
- 최초 조사에서는 앱의 자동 중단과 저장 상태를 유지했다. 이후 사용자가 직접 차단 상태 파일을 옮겨 재개했다.
- 차단 파일에 따른 원래 대기 만료값은 9/28 약 11:58:37이었다. **앱이 정한 재시도 대기 시간이며 쿠팡이 알려준 해제 시간은 아니다.** 실제로는 그 전에 같은 출력 폴더에서 저장된 결과를 이어받아 성공했다.
- 원인을 더 좁히려면 별도 통제된 비교가 필요하다. 이번 조사에서는 실행 중인 다른 작업에 영향을 주는 신규 접속 실험을 추가하지 않았다.

전체 GUI 로그·화면·읽기 전용 진단 스크립트는 호스트 `%LOCALAPPDATA%\Temp\codex-coupang-debug`에 보존했다. 저장된 상품·판매자 결과나 앱 코드는 변경하지 않았다.
