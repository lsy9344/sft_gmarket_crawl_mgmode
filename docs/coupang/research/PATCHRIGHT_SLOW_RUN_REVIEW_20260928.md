# Patchright 실험판의 느린 수집 방식과 현재 앱 비교

- 검토일: 2026-09-28 KST.
- 질문: 현재 방식이면 계속 차단되는가, Patchright 워크트리처럼 천천히 하는 방법만 남았는가.
- 검토 범위: 코드와 저장된 실행 기록. 이번 검토에서 수집 실행이나 앱 변경은 하지 않았다.

## 판단

현재 앱은 반복 차단 때문에 안정적인 무인 완주가 검증되지 않았다. 하지만 모든 실행이 항상 실패하는 것도 아니다. 완료 6개 카테고리의 상품 507행·판매자 344행(고유 상품 504개·판매자 319명)이 남아 있다.

**작은 묶음으로 수집하고 쉬는 운영은 비교할 가치가 있다. 속도만 낮추면 해결된다거나 이 방법만 가능하다는 증거는 없다.** 특히 오늘 12:58~13:01 실패는 상품 목록을 읽기 전, 세 번의 첫 홈 접속에서 발생했다. 이 실행에서 상품 요청을 빠르게 보낸 것이 원인이라는 설명은 맞지 않는다. 과거 요청 이력의 영향까지 배제할 수 있다는 뜻은 아니다.

## 현재 코드에서 확인한 차이

| 항목 | 현재 앱의 쿠팡 카테고리 | Patchright 실험 워크트리 |
|---|---|---|
| 조작 도구 | Patchright | Patchright |
| 브라우저 | 내려받은 Chromium | 설치된 Google Chrome |
| 브라우저 기록 | 시도마다 새 폴더 생성, 종료 시 삭제 | 전용 Chrome 프로필 재사용 |
| 목록 회선 | Decodo | 확인한 실험 기본 경로는 직접 회선 |
| 판매자 회선 | 기본값은 직접 회선 | 직접 회선 |
| 진행 방식 | 페이지 간 기본 15~20초, 판매자 간 기본 2.5~3.5초 | 작은 묶음과 예약 대기 중심 |
| 진행 저장 | 카테고리별 SQLite | 별도 JSON 상태와 예약 기록 |

현재 앱의 프로필은 한 번 실행하는 동안 디스크에 저장되는 형식이지만, `decodo_run.py`가 매번 난수 이름을 만들고 끝나면 지우므로 다음 시도에 방문 기록을 이어 쓰는 방식은 아니다. 이것이 이번 차단 원인이라고 확정하지 않는다.

## 현재 실패의 정확한 범위

[회수한 원본 로그](evidence-direct-block-20260928/sandbox-proxy-home-block-1301.log)를 다시 집계했다.

- Chromium 세션 시작 3번, 웜업 시작 3번.
- 홈 HTTP 403: 12:58:42, 13:00:18, 13:01:54.
- 카테고리 목록 단계 진입 0번.
- 서로 다른 Decodo 출구 IP 세 개에서 발생. IP 영향 없음이나 특정 브라우저 신호 때문이라고 확정할 수 없음.
- 상세: [이번 첫 홈 차단 기록](SANDBOX_PROXY_HOME_BLOCK_20260928.md).

판매자 단계만 프록시로 바꾸는 작업은 이 선행 홈 차단을 해결했음을 입증하지 못했다. [실제 검증 상태](VENDOR_PROXY_VERIFICATION_20260928.md)에서도 목록 진입 실패로 판매자 단계 연속 검증에 도달하지 못했다.

## 실험 기록의 해석

워크트리의 현재 코드와 [실험 보고서](../../../../sft_gmarket_crawl_mgmode-patchright-canary/docs/coupang/PATCHRIGHT_EXPERIMENT_REPORT.md#L866)를 직접 확인했다.

- 목록 코드의 페이지 간 대기는 15초다. 현재 앱의 15~20초보다 느리지 않다. 판매자 단계도 약 3초로 현재 기본 2.5~3.5초와 비슷하다. 핵심 운영 차이는 **한 번에 처리하는 양을 제한하고 실행 사이 간격을 길게 두는 것**이다.
- 마지막 보고된 예약은 80분마다 실행을 시작하고, 한 번에 목록 최대 8페이지 또는 판매자 처리 단계 하나를 실행한다. 판매자 단계의 `--limit=130`은 입력 상품 처리 한도이며, 고유 판매자 130명을 보장하는 숫자가 아니다. 예약 시작 간격 80분과 작업 종료 뒤 휴식 80분은 다르다.
- 목록 처리·판매자 처리를 병렬로 돌리지 않는다. 예약 중복 실행은 `IgnoreNew`로 막는다. 오류·503·차단이면 남은 예약을 끄도록 되어 있다.
- 9월 8일 16:06 보고서는 15:27까지 80분 작업 6회 성공, 누적 카테고리 9/12개, 상품 7,426개(연결 완료 7,420개), 판매자 1,563명을 기록한다. 이 누적 수량 전부를 80분 작업 6회에서 얻었다는 뜻은 아니다.
- 그 전에는 연속 목록 작업에서 HTTP 403이 있었고, 61분 예약이 여러 번 성공한 뒤에도 HTTP 503으로 멈췄다. 503만으로 봇 차단을 확정하지 않는다.
- 9월 10일까지 후속 예약을 등록했다는 기록은 있지만, 예약 등록을 전체 완주로 해석할 수 없다. 이번에는 과거 전체 원본 데이터나 당시 예약의 현재 상태를 재검증하지 않았다.

소스: [브라우저 생성](../../../../sft_gmarket_crawl_mgmode-patchright-canary/app/core/coupang/patchright_canary.py#L463), [단계별 단일 실행](../../../../sft_gmarket_crawl_mgmode-patchright-canary/scripts/prototypes/coupang_patchright_fruit_pipeline.py#L150), [80분 예약](../../../../sft_gmarket_crawl_mgmode-patchright-canary/scripts/prototypes/register_patchright_80min_continuation.ps1#L7).

과거 성공 기록은 현재 Sandbox에서 같은 방식의 성공률을 보장하지 않는다.

Google Chrome, 프로필 유지, 회선, 작업량, 대기 시간 등 여러 조건이 달라지므로 과거 결과만 보고 성공 원인을 대기 시간 하나로 좁힐 수 없다. 공식 Patchright도 Chrome 사용을 권장하지만 우리 환경에서 Chromium보다 낫다는 실측 결과는 아니다. [공식 권장 사항](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright-python#best-practice---use-chrome-without-fingerprint-injection).

Akamai는 요청 헤더·브라우저 버전의 이상, 브라우저 확인, 일부 구간의 행동 등을 검사할 수 있다고 설명한다. 이는 제품 기능이며 쿠팡의 이번 거부 규칙을 공개한 자료가 아니다. [공식 탐지 설명](https://techdocs.akamai.com/cloud-security/docs/detection-methods).

## 다음 판단 기준

1. 현재와 실험 방식은 이미 같은 Patchright를 사용한다는 점을 전제로 비교한다.
2. 첫 접속 거부와 연속 수집 중 거부를 따로 평가한다.
3. 작은 실제 작업의 목록·판매자 정보·저장·중단 후 재개까지 확인한 뒤 작업량을 판단한다.
4. 거부가 나오면 해당 실행을 중단하고 기록을 보존한다. 대기 시간을 근거 없이 고정된 정답으로 취급하지 않는다.
5. 기존 완료 결과와 진행 DB는 유지한다. 실험 워크트리의 JSON 진행 파일이 현재 앱 DB와 호환된다고 가정하지 않는다.

이번 검토는 수정·배포나 실수집 재개가 아니라 운영 선택에 대한 판단이다.
