## 확인한 원인과 실패 지점

**Decodo를 사용하는 새 Chromium 세션의 첫 쿠팡 홈 접속이 Akamai 접근 거부(HTTP 403)를 받았다.** 앱은 한국 프록시 회선 확인에 성공한 뒤 3개의 서로 다른 출구 IP로 시도했으나, 모두 `Phase 1: 웜업`에서 멈췄다.

| 시도 | 확인된 Decodo 출구 IP | 첫 홈 403 시각(KST) |
|---|---|---|
| 1 | 61.74.244.21 | 12:58:42 |
| 2 | 119.202.230.74 | 13:00:18 |
| 3 | 182.230.127.154 | 13:01:54 |

마지막 응답 Reference: `18.fa3c117.1790568115.8be2efa6`. 각 응답의 차단 HTML 저장 경로도 로그에 남아 있다. 이번 조사에서는 해당 HTML을 추가 회수하거나 쿠팡에 재현 요청을 보내지 않았다.

이전 23:58·00:50 사건은 프록시 목록을 끝낸 뒤 **직접 회선으로 바꾼 판매자용 홈 접속**에서 차단됐다. 이번에는 **초기 Decodo 홈 접속**이 거부돼, 직접 회선 전환과 판매자 API에 도달하지 못했다. 현재 현상을 집 IP의 누적 점수 하나로 설명할 수 없다.

## 이어받기 자료와 대기 게이트

- 로그가 완료한 6개 카테고리를 인식하고 기존 결과를 재사용했다.
- 라면/파스타/면(432572)의 진행 기록도 `마지막 확인 페이지 19 / 상품 39개 / 확인된 판매자 0명`으로 읽혔다.
- 이번 실패는 저장 결과를 읽지 못한 오류가 아니라 이후 네트워크 접근 거부다. 조사에서는 결과 파일이나 진행 DB를 변경하지 않았다.
- 00:50:21에 기록했던 12시간 대기값은 12:50:21에 만료되는 값이다. 실제로 12:58 이후 새 회선 조회와 쿠팡 요청이 실행됐으므로, 이번 오류는 대기 게이트가 실행을 막은 것이 아니다.
- 이번 3회 실패는 모두 프록시 차단으로 분류됐고, 새 12시간 직접 회선 차단 기록을 남기지 않는다는 로그가 있다.

## 저장된 목록이 있는데도 홈에 먼저 접속하는 이유

현재 `search_crawler.py:_run_pipeline`은 `_warmup_home(page)`를 먼저 실행한 다음 저장된 상품과 목록 완료 상태를 복원한다. 따라서 상품 목록 39개가 이미 있어도 새 세션의 쿠팡 홈 접속을 반드시 먼저 거친다. 이번에는 이 선행 단계가 실패해 저장된 목록으로 판매자 연결을 시작하지 못했다.

## 판매자 프록시 전환 제안과의 관계

[판매자 프록시 검증 보고서](VENDOR_PROXY_VERIFICATION_20260928.md)에는 01:45~01:53 시험에서 Decodo 회선 4개가 홈 또는 첫 카테고리 페이지에서 막혔고, 판매자 단계 실증에 도달하지 못했다고 기록돼 있다. 저장된 `full-run.stdout`에서도 홈 403 두 번, 홈 성공 후 첫 목록 403 한 번을 확인했다.

코드에는 `vendor_phase_line` 검증 설정이 추가됐지만 기본값은 `direct`이고, `decodo_run.py`에 `proxy` 기본 전환은 없다. 이번 실행의 시작 안내 역시 판매자 정보는 이 PC 회선이라고 표시한다. 다만 이번 실패는 해당 분기보다 앞에서 발생하므로, 판매자 전환 분기만 변경하는 것으로 이번 최초 홈 403이 해결됐다고 판단할 수 없다.

## 아직 확정할 수 없는 부분

쿠팡이 왜 이 세 요청을 거부했는지 결정 규칙은 응답 로그에 없다. 프록시 출구의 상태, 브라우저의 요청 특성, 새 세션 상태 등의 영향을 이 자료만으로 분리할 수 없다. 3개 IP에서 실패했다는 사실만으로 IP 영향이 없거나 특정 브라우저 신호가 원인이라고 확정하지 않는다.

후속 진단의 초점은 **실제 Windows Chromium의 Decodo 초기 접속**이다. 실수집과 동시에 별도 시험을 하지 않고, 비교할 경우 동일 회선에서 요청 방식만 바꾸는 등 조건을 분리해 확인해야 한다. 판매자 단계의 성공 여부와 중단·재개 검증은 초기 접속 문제와 구분해 판단한다. 이번 조사에서는 접속 비교 실험·코드 수정·재시작을 하지 않았다.
