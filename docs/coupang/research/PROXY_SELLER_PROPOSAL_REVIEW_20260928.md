# 판매자 조회를 Decodo로 옮기자는 제안의 근거 검토

- 요청: “집 IP 누적 점수 때문에 차단됐으며, 판매자 단계를 Decodo로 옮기면 해결된다”는 다른 에이전트의 분석과 신뢰도 재검토.
- 검토일: 2026-09-28 KST.
- 범위: 저장된 시험 원본·과거 기록·현재 코드의 읽기 전용 검토. 새 쿠팡 요청, 앱 코드 변경, 빌드·재배포는 하지 않았다.

## 판단

전체 설명의 근거 충족도를 주관적으로 **약 60/100**으로 평가한다. 통계로 계산한 정확도나 향후 실행의 성공 확률이 아니다. 원인 단정과 개선 제안은 별도로 평가해야 한다.

| 항목 | 평가 |
|---|---|
| 집 직접 회선으로 바꾼 첫 홈 접속에서 차단 | 앱 로그에서 두 번 확인됨 |
| 집 IP의 누적 점수가 임계를 넘었음 | 가능한 설명이지만 점수·임계값·결정 신호는 측정하지 못함. 원인 설명에 대한 신뢰는 약 30/100 |
| Decodo에서도 판매자 API가 성공할 수 있음 | 원본 시험에서 1건의 HTTP 200과 판매자 JSON 시작 부분을 확인함 |
| 판매자 단계의 프록시 유지 방안을 우선 검증 | 타당한 다음 후보. 검증 우선순위에 대한 신뢰 약 80/100; 앱 완주 성공률을 뜻하지 않음 |
| 전환하면 차단이 사라지고 이어받기도 그대로 보장 | 전체 앱 흐름·연속 수집·재개 검증 전에는 보장할 수 없음 |

## 새 시험의 실제 증거

다른 에이전트의 원본은 주장한 보고서 증거 폴더가 아니라 `/tmp/coupang-blockhunt/vendor_proxy_test.py`와 `.json`에서 찾았다. 결과 파일 수정 시각은 9/28 00:53:14 KST이며, 개별 요청의 시각은 기록하지 않았다. 이번 검토에서 [결과 사본](evidence-direct-block-20260928/vendor-proxy-test-0053.json)과 [검토 메타데이터·해시](evidence-direct-block-20260928/vendor-proxy-test-review-metadata.json)를 보존했다.

- Decodo 출구 IP: `121.151.227.230`.
- 도구: 브라우저 없이 `curl_cffi.requests`, `impersonate='chrome150'`.
- `www.coupang.com/`: HTTP 200.
- `shop.coupang.com/api/v1/store/getStoreReview?vendorId=A00017880&urlName=A00017880`: **HTTP 200**, 응답 문자 수 1,010. 저장된 앞 120자에 해당 판매자 ID, 평점 집계, 업체명 시작 부분이 있다.
- `shop.coupang.com/`: HTTP 404. 스토어 루트의 결과이며 앱이 실제 사용하는 특정 판매자 스토어 페이지의 시험을 대신하지 않는다.

이 결과는 “프록시에서는 판매자 조회가 언제나 불가능하다”는 일반화에 대한 반례다. 그러나 **한 회선·한 판매자·한 번의 API 요청**이다. 앱의 상품→판매자 연결 API, 실제 Chromium 브라우저의 요청, 필수 사업자 항목 전체, 여러 판매자 연속 처리, 차단 후 재개는 시험하지 않았다. 전체 응답이 보존되지 않아 대표자·전화·이메일 등 모든 필드가 정상인지 이번 원본만으로 확인할 수도 없다.

## 과거 기록과 맞지 않는 설명

제안의 “9월 당시 Camoufox는 회선과 무관하게 모든 요청이 403이었다”는 전제는 과거 기록과 충돌한다.

[9월 8~9일 조사 §9](../BRIGHTDATA_AKAMAI_REVIEW_20260908.md)에 따르면:

- 당시 문제 회선은 **Bright Data ISP**였다. 이번 신규 시험은 **Decodo Residential**이므로 공급자·회선 유형도 달라졌다.
- 같은 Camoufox에서 상품→판매자 연결은 프록시·직접 회선 모두 HTTP 200이었다.
- 판매자정보만 그 ISP 프록시에서 403, 직접 회선의 새 Camoufox에서는 200이었다.
- 실제 상품 연결 1,794개, 판매자 514명 처리 성공 기록이 있다.

같은 문서 §15에도 9월 10일 Camoufox+Decodo 목록과 직접 판매자 조회 조합으로 상품 791개·판매자 408명·차단 0건이 기록됐다. 또한 9월 27일 실제 Sandbox Camoufox의 19:50 성공도 남아 있다.

따라서 당시 관측을 단순한 착각으로 폐기할 수 없다. 정확한 정정은 **특정 시점·특정 ISP 프록시에서의 실패를 현재의 모든 프록시에 일반화하면 안 된다**는 것이다. 새 시험은 그 일반화를 재검토할 근거다. 구형 브라우저 지문 하나가 과거 결과 전체를 설명한다는 결론은 아니다.

## 집 IP 점수와 회복 시간

[실제 앱 로그](SANDBOX_DIRECT_BLOCK_20260928.md)는 23:58 직접 홈 403, 00:37 새 직접 세션 성공, 00:40 판매자 36명 완료, 00:50 다른 새 직접 세션의 홈 403을 보여준다. 이로써 직접 세션에서 성공·실패가 반복됐다는 것은 확인된다.

그러나 다음 값은 관찰하지 못했다: 집 IP의 내부 점수, 점수의 증감, 임계값, 세 번째 재시도가 회복을 늦추는 정도. 과거 재시도 실패나 코드 주석만으로 이 값을 추론해 사실로 사용할 수 없다. 12시간 휴식 뒤 남은 카테고리가 완주한다는 보장도 없다.

Akamai 공식 문서는 여러 요청 특성 및 점수를 쓰는 탐지와 운영자별 대응 설정을 설명한다. 제품에 그런 기능이 있다는 사실이 이번 쿠팡 차단에서 특정 IP 점수 규칙이 발동했다는 증거는 아니다. [Detection methods](https://techdocs.akamai.com/cloud-security/docs/detection-methods), [Handle adversarial bots](https://techdocs.akamai.com/cloud-security/docs/handle-adversarial-bots).

## A안을 실제 적용하기 전 확인할 범위

코드 검토에서는 “이어받기 구조는 그대로”에도 구분이 필요했다. 상품 목록의 완료 표시, 저장된 매핑, 판매자별 저장 자료는 재사용할 수 있다. 하지만 `_direct_session`은 현재 직접 전환 함수에서만 설정된다. 전환을 없애면 판매자 단계의 차단도 프록시 차단으로 분류되어 직접 회선용 12시간 기록을 남기지 않고, Decodo 회선을 바꿔 최대 3번 재시도하는 경로로 간다. **자료 저장 방식이 유지돼도 실패 후 재시도·대기 동작은 바뀐다.** 매핑은 배치 전체 종료 후 저장되고 판매자 결과는 건별로 저장되는 차이도 재개 검증에 포함해야 한다.

1. 실제 배포용 Chromium에서 목록을 읽은 동일 Decodo 세션으로 스토어 페이지와 상품→판매자 연결 API까지 정상 진행되는지.
2. 판매자 응답의 필수 항목과 저장 결과가 맞는지, 여러 판매자를 연속 처리해도 정상인지.
3. 일부 완료 뒤 중단·재개 시 저장 상품·연결·판매자 기록을 올바르게 재사용하는지.
4. 프록시 판매자 단계의 차단을 직접 회선 차단으로 잘못 기록하지 않는지, 이전 직접 차단 파일이 새 경로를 불필요하게 막지 않는지.
5. 판매자 단계까지 Decodo를 사용할 때 늘어나는 실제 사용량과 요금.

직접 쿠팡 접속을 없애도록 구현하면 그 직접 접속 경로는 없어질 수 있다. 프록시에서도 접근 거부·만료·통신 오류는 별도로 발생할 수 있으므로, 이를 전체 차단 문제가 해결된 것으로 표현하지 않는다. **A안은 우선 검증할 만한 방향이며, 근본 원인 확정이나 무차단 보장을 뜻하지 않는다.**
